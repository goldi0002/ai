# TinyLM-50

A ~49M-parameter decoder-only transformer with a full local stack: SentencePiece
tokenizer, data pipeline, pretraining and instruction-tuning loops, a tool-using
agent, an offline SQLite + FTS5 research index, persistent memory, INT8/INT4
weight quantisation and a CLI.

Everything runs offline. There is no API key, no vendor SDK and no shell tool.

## Honest status

This repository contains a **working pipeline and a smoke-scale trained model**,
not a useful assistant.

- The architecture is complete and its parameter count is verified:
  **49,035,776 parameters**.
- The shipped checkpoint was trained for **240 pretraining steps (61,200 tokens,
  ~0.35 epoch of the 176,294-token corpus)** and then **350 SFT steps on 18
  training conversations**. That is enough to prove every path works; it is not
  enough to learn language.
- The pretraining corpus is **synthetic seed text** generated by
  `data/seed_corpus.py`. It is explicitly labelled synthetic and is not a
  substitute for a real corpus.
- After SFT, held-out perplexity on the pretraining validation split is
  **21,413**, i.e. worse than a uniform distribution over 16,000 tokens
  (16,000). The SFT checkpoint memorised its 18 examples and lost general
  modelling ability. The agent demo below shows exactly that: tool plumbing
  works, language quality does not.
- No benchmark number in this README is copied from another project; each one
  was measured in this workspace and is reproduced by the commands shown.

If you want a model that answers well, train on a licensed corpus for many more
steps (see [Next steps](#next-steps)). The code is ready for that; the data is
not included.

## Quick start

Python 3.10+ and a CPU are enough. The project was developed in a local
virtualenv because the system site-packages is read-only.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 1. Reproducible synthetic seed corpus (~1.2 MiB, labelled synthetic)
.venv/bin/python -m data.prepare seed

# 2. Clean, filter, deduplicate, split
.venv/bin/python -m data.prepare prepare

# 3. Train the 16k SentencePiece tokenizer
.venv/bin/python -m data.prepare tokenize

# 4. Pack uint16 token sequences (256 tokens here to fit a 2-vCPU box)
.venv/bin/python -m data.prepare pack --seq-len 256

# 5. Pretrain (this is the exact smoke run reported below)
.venv/bin/python -m training.train --max-steps 40 --batch-size 1 \
  --grad-accum 1 --lr 1e-3 --log-every 5 --eval-every 0 \
  --checkpoint-every 10 --run-name pretrain_smoke

# 6. Instruction-tune on the 20 curated tool-use conversations
.venv/bin/python -m training.sft --init checkpoints/latest.pt \
  --max-steps 100 --batch-size 2 --grad-accum 1 --lr 2e-4 \
  --eval-every 50 --log-every 10 --run-name sft_smoke

# 7. Index the research library, then chat
.venv/bin/python -m runtime.cli research ingest --dir datasets/documents
.venv/bin/python -m runtime.cli chat
```

`chat` uses the checkpoint path from `configs/tiny50.yaml`
(`checkpoints/latest.pt`). Expect poor prose; the diagnostics printed on stderr
show which tools ran and any citations returned.

## Data pipeline

`data/prepare.py` implements:

1. **Seed** — deterministic synthetic text in seven categories (technical,
   prose, programming, Q&A, arithmetic, dialogue). Every file starts with a
   header saying it is synthetic. A separate generated identifier corpus is used
   **only** for tokenizer training; a 16k BPE vocabulary needs more distinct
   substrings than hand-written seed prose contains. It is never pretraining
   text.
2. **Prepare** — NFKC normalisation, control-character removal, quality filters
   (length, symbol ratio, repetitive runs, diversity, URL-heavy pages),
   exact SHA-256 duplicate removal, SimHash near-duplicate removal, then a
   deterministic document-level train/validation split. A manifest records
   counts, drop reasons, hashes and provenance.
3. **Tokenize** — SentencePiece BPE, vocab 16,000, `byte_fallback=True`,
   case-preserving `nmt_nfkc`. Special tokens are user-defined symbols and their
   ids are verified at load time:
   `<pad>=0 <unk>=1 <bos>=2 <eos>=3 <user>=4 <assistant>=5 <system>=6
   <tool_call>=7 <tool_result>=8 <research>=9 <evidence>=10 <final>=11`.
4. **Pack** — documents become `<bos> text <eos>`, concatenated and sliced into
   fixed-length `uint16` sequences plus an index. Training shifts inputs by one
   token so position *i* never predicts its own token.

Measured on this workspace: 7 seed documents, 697,406 train characters, 673
training sequences × 256 tokens, 176,294 total tokens, 16,000-piece tokenizer.

External corpora are never downloaded automatically. `datasets/sources.yaml`
lists candidates, and `python -m data.fetch --list` / `--source NAME --confirm`
prints the licence and records a SHA-256 in `datasets/sources_manifest.json`.

## Training

Both loops share `training/trainer.py`: gradient accumulation, AdamW with no
weight decay on norms/biases, linear warmup + cosine decay, gradient clipping,
autocast on supported hardware, JSONL logs, evaluation and resumable
checkpoints. A checkpoint stores the model config, tokenizer ids, step, token
count, optimiser state and training config, so it is self-describing.

Measured runs on this machine (CPU, 2 vCPU, 3 GB RAM):

| Run | Steps | Tokens | Train loss first → last | Validation |
| --- | ---: | ---: | --- | --- |
| Pretrain | 40 | 10,200 | 10.599 → 5.078 | loss 8.383, ppl 4,374 |
| Pretrain (continued to 240) | 240 | 61,200 | 6.186 → 2.633 | loss 7.611, ppl 2,021 |
| SFT | 100 | 16,160 | 9.223 → 1.713 | loss 4.207, ppl 67.2 |
| SFT (continued to 350) | 350 | 56,518 | 1.361 → 0.004 | loss 4.170, ppl 64.7 |

Notes:

- Pretraining throughput was ~300 tokens/s; SFT ~168 tokens/s.
- The 240-step pretrain took 177.7 s (43.2 s for the first 40 steps); the
  100-step SFT took 111.7 s; the continuation to 350 took 262.5 s.
- The pretraining validation split is drawn from the same synthetic templates,
  so its perplexity is optimistic. Even so, the model is heavily overfit.
- SFT loss masks everything except assistant tokens (including tool-call JSON).
  System, user and tool-result tokens are context, never targets.
- SFT evaluation uses one held-out conversation; treat it as a smoke signal.

## Agent and tools

Tool-call format (plain text, no vendor API):

```
<tool_call>{"name": "calculator", "arguments": {"expression": "17*23+4"}}
```

One JSON object per call. The runtime parses it, executes the named tool, and
feeds the observation back as `<tool_result>{"ok": true, "content": ...}`. A
final answer follows `<final>`.

Registered tools:

| Tool | Arguments | Purpose |
| --- | --- | --- |
| `calculator` | `expression` | AST allowlist arithmetic; no `eval` |
| `local_search` | `query`, `limit` | BM25 search with citations |
| `read_document` | `path`, `max_chars` | Read text/Markdown/Python/PDF inside the document root |
| `list_files` | `pattern`, `max_results` | List documents |
| `retrieve_memory` | `query`, `limit` | Read saved notes |
| `save_memory` | `key`, `content`, `tags`, `importance` | Create or update a note |

The loop enforces `max_iterations`, `max_tool_calls_per_turn`, a per-tool
timeout, a context-token budget and a duplicate-call guard. Parse errors and
tool failures are returned to the model as errors; malformed JSON gets one
repair attempt. There is no shell, no arbitrary code execution, and file paths
are resolved against `datasets/documents` with an escape check.

The prompt layout matches `training/data.py` exactly; a 256-token checkpoint
cannot afford the long system prompt, so the runtime defaults to the same short
system prompt used during SFT (`COMPACT_SYSTEM_PROMPT`).

## Research engine

`tools/research.py` uses SQLite with FTS5 in external-content mode:

- `documents` (path, title, SHA-256, size, chunk count, ingest time)
- `chunks` (document id, ordinal, character offset, text)
- `chunks_fts` with `porter unicode61` stemming and BM25 ranking
- triggers keep the index in sync on insert/update/delete

Queries are converted to quoted literal terms, so FTS5 operators in user text
cannot raise syntax errors. Search tries AND first, then OR, and every hit
carries a citation with title, path, chunk ordinal and character offsets.

CLI:

```bash
.venv/bin/python -m runtime.cli research ingest --dir datasets/documents
.venv/bin/python -m runtime.cli research search "BM25 ranking" --limit 3
.venv/bin/python -m runtime.cli research list
.venv/bin/python -m runtime.cli research stats
.venv/bin/python -m runtime.cli research remove bm25_and_fts5.md
```

Measured index: 5 documents, 21 chunks, 13,659 characters. Search for
`quantisation` returns 3 hits in 0.45 ms (mean of 5 runs).

## Memory

`memory/store.py` stores keyed notes in the same SQLite database, with an FTS5
index over key, content and tags. Saving an existing key updates it in place and
preserves `created_at`. Retrieval can be searched or ordered by importance.
`to_context()` caps injected text so memory cannot crowd out the conversation.

```bash
.venv/bin/python -m runtime.cli memory save user_timezone "Europe/Berlin" --tags preference --importance 0.8
.venv/bin/python -m runtime.cli memory list
.venv/bin/python -m runtime.cli memory search timezone
.venv/bin/python -m runtime.cli memory delete user_timezone
```

## Inference and CLI

```bash
.venv/bin/python -m runtime.cli info
.venv/bin/python -m runtime.cli generate "The capital of France is" --max-new-tokens 32
.venv/bin/python -m runtime.cli chat
.venv/bin/python -m runtime.cli tools                 # schemas
.venv/bin/python -m runtime.cli tools calculator --arguments '{"expression":"sqrt(2)*10"}'
```

`load_model()` refuses a checkpoint whose vocabulary or special-token ids do not
match the tokenizer. Generation uses a KV cache; a regression test checks that
cached and uncached greedy decoding produce identical tokens.

## Quantisation

Weight-only, symmetric, per-output-channel. Embeddings and the tied LM head stay
in float32; 98 `nn.Linear` modules (40,828,928 weights) are quantised. The INT4
path packs two signed nibbles per byte and is marked experimental.

| Format | File size | FP32 weights ÷ file | Quantised-weight ratio | Validation loss Δ |
| --- | ---: | ---: | ---: | ---: |
| INT8 | 74,003,667 B (70.6 MiB) | 2.65× | 3.97× | −0.0002 |
| INT4 | 53,589,203 B (51.1 MiB) | 3.66× | 7.90× | +0.0229 |

```bash
.venv/bin/python -m runtime.cli quantize --bits 8 --eval-batches 5
.venv/bin/python -m runtime.cli quantize --bits 4 --eval-batches 5
```

Each run writes `checkpoints/tiny50.int{8,4}.pt` and a sibling `.json` report.
The file still contains float32 embeddings and norms, which is why it is not 4×
or 8× smaller. The implementation dequantises weights inside every forward pass;
**no speedup is claimed and none was measured** — the win is checkpoint size.

## Held-out tool-selection evaluation

`datasets/instructions/tool_selection_eval.jsonl` contains 25 labelled prompts
that are **not** in the SFT file (a test enforces that, including substring
matches after normalisation). Twenty require a specific tool and five require
no tool; one asks for two tools in one turn.

```bash
.venv/bin/python -m runtime.cli eval-tools --verbose
# writes storage/tool_selection_eval.json
```

Metrics are computed from the tool calls the agent actually executed:

- **first-tool accuracy** — first executed tool equals the first expected tool;
- **exact-set accuracy** — the set of executed tools equals the expected set;
- **invalid-call rate** — cases with a failed call, unknown tool or parse error;
- **missing-tool rate** — tool-required prompts that executed no tool;
- **no-tool false-positive rate** — direct prompts that called a tool.

Measured on the shipped checkpoint (`temperature=0`, greedy, two iterations):

| Metric | Result |
| --- | ---: |
| Cases | 25 (20 tool, 5 direct) |
| First-tool accuracy | **24.0%** (6/25) |
| Exact-set accuracy | **24.0%** (6/25) |
| Invalid-call rate | 36.0% (9/25) |
| Missing-tool rate | 80.0% (16/20) |
| No-tool false positives | 20.0% (1/5) |
| Cases with parse errors | 7 |
| Wall clock | 43.6 s |

| Category | n | First | Exact | Invalid |
| --- | ---: | ---: | ---: | ---: |
| calculator | 6 | 33% | 33% | 33% |
| local_search | 5 | 0% | 0% | 20% |
| read_document | 2 | 0% | 0% | 100% |
| list_files | 2 | 0% | 0% | 50% |
| retrieve_memory | 2 | 0% | 0% | 50% |
| save_memory | 2 | 0% | 0% | 0% |
| no_tool | 4 | 75% | 75% | 50% |
| unavailable_tool | 1 | 100% | 100% | 0% |
| multi_tool | 1 | 0% | 0% | 0% |

Re-running with a larger generation budget (`--max-new-tokens 160
--max-context-tokens 90`, report `storage/tool_selection_eval_160.json`)
produced identical metrics, so the result is not an artefact of truncated JSON.

**Read this number carefully.** The two calculator “successes” both called
`calculator` with the expression `17*23+4` for unrelated questions (“19 percent
of 250”, “seconds in 3.5 hours”). The call was selected, but the argument was a
memorised fragment from SFT. Selection accuracy therefore overstates useful
behaviour; argument correctness was not scored and is clearly poor. The
dominant failure is not a near miss: on 16 of 20 tool prompts the model emitted
no usable call at all.

Implication for more SFT data: adding more examples in the same style will
mostly teach more memorised fragments. The next data pass should add (a) varied
wording for the same intent, (b) negative/no-tool examples, (c) argument-level
supervision with diverse numbers and paths, and (d) longer, cleaner tool-call
JSON targets. Re-run `eval-tools` after each change and compare against this
24% baseline.

```
tools: []

```

This is the honest output. The calculator call is correct and executed; the
memory write is correct; retrieval was not selected because the model is too
weak. The prose is not trustworthy.

## Hardware notes

- Training 49M parameters at 256 tokens, batch 1 completed on this 3 GB
  container at ~300 tokens/s. Gradient accumulation is implemented but was left
  at 1 for the smoke runs so the step counts are easy to compare.
- Generation is ~41 tokens/s on 2 vCPU with the KV cache. Uncached decoding was
  not benchmarked; it re-runs the prefix and is expected to be slower. A cache
  bug found during development (causal mask applied to a single-query step) is
  fixed and covered by a test.
- A full 1024-token context, larger batches or bf16 need a GPU; the code paths
  exist (`precision: auto|bf16|fp16|fp32`, `gradient_checkpointing`,
  `torch.compile`) but were not exercised on this CPU box.
- Checkpoints include optimiser state (588 MB). Weights alone are ~196 MB in
  float32.

## Limitations

- The model is not trained to a useful quality level; see the perplexity.
- The corpus is synthetic and tiny. It cannot teach facts, reasoning or style.
- SFT overfits 18 examples; held-out conversation loss is 4.17.
- The shipped checkpoint has `max_seq_len=256` because the packing run used 256.
  The architecture supports 1024; retrain with `--seq-len 1024` to use it.
- Tool selection on the 25 held-out prompts is 24% exact-set accuracy, and the
  two calculator “hits” reused a memorised expression. This checkpoint should
  not be used for agent behaviour; it validates the plumbing only.
- PDF reading depends on `pypdf` and its extraction quality.
- Quantisation is a simple reference implementation, not a fused kernel.
- No tokenizer or model files are committed; the pipeline recreates them.

## Next steps

   `python -m data.fetch --source NAME --confirm`, then prepare/tokenize/pack at
   1024 tokens.
2. Pretrain for tens of thousands of steps with gradient accumulation and bf16

3. Expand the instruction set well beyond 20 examples, including negative

4. Evaluate tool selection with a held-out labelled set rather than eyeballing
   transcripts.
5. Only then consider quantisation trade-offs; measure both size and latency.
